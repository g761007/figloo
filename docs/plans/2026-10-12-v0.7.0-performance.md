# v0.7.0：效能

日期：2026-10-12
狀態：M1 完成（ad061bf）；M2 完成（2026-10-12），等待 commit
依據：[產品化計畫](2026-10-06-productization-and-reliability.md)第 4.9 節、第 4.10 節的 Performance 基準與 v0.7.0；[ROADMAP](../../ROADMAP.md) 的 0.7.0

## 目標

拍快照變快，而且快多少有數字。再拍同一個畫面時只重讀有變動的部分，前提是找得到不必逐層選取就能看出屬性變動的訊號，也就是產品化計畫第 4.9 節的關卡。

## 現況

- 已知的數字都來自 2026-10-01：278 層 34.7 到 38.8 秒，其中截圖 3.5 秒、走訪 4.5 到 5.6 秒，其餘是逐層讀取，每層約 0.11 秒；198 層 28.8 秒。之後加了分組標題、parse guard 與背景暫停，沒有重新量過。
- 伺服器的 log 只記總時間、走訪時間與 UI 操作次數。截圖與逐層讀取內部的各個步驟沒有分開計時。
- 逐層讀取時，每一層的步驟是：在圖層面板找到那一列（必要時捲動）、點選並等 Figma 標示選取、等屬性面板換成這一層、解析屬性面板與匯出區塊、等 mirror 標出位置。
- 從程式看得到的固定等待：
  - 屬性面板內容變了、但標題不是圖層名稱時（例如圖片顯示檔名），等滿 500 ms；標題是圖層名稱、但內容沒變時（相鄰兩層長得一樣），等滿 400 ms。
  - 非文字圖層的位置 mirror 還沒標出時，最多等 300 ms。mirror 從來不標隱藏圖層，所以每個隱藏圖層都等滿 300 ms，而走訪結束時就已經知道哪些圖層是隱藏的。
  - 截圖：縮放後等 500 ms 動畫，再等 200 ms，然後等縮放提示消失，最多 4 秒，實測約 3 秒。
- 快照已有 24 小時的快取（`snapshotTtlHours`）與 `refresh`。再拍同一個 root 時會和上一次比較，標出新增、變更與移除的圖層，但仍是整個重讀。

## 里程碑

每個里程碑完成後先不 commit，回報結果，等使用者同意後再 commit 並 push。

### M1：分段計時

- extension 在快照結果加上各階段的時間：截圖（縮放、等提示消失）、走訪、逐層讀取各步驟的總和、等滿 400 ms、500 ms 與 300 ms 的次數、收回展開的圖層與還原畫面。只有數字，沒有圖層名稱或 ref。
- 伺服器把它寫進 log，不放進 agent 看到的工具結果。協定只加選填欄位，不改 `PROTOCOL_VERSION`。
- 新增 `pnpm bench:snapshot`：用登入版 canary 的 profile，對設定的幾個 frame 以 `refresh: true` 各拍 N 次，列出各階段的中位數。

驗證：計時累計的單元測試；整合測試的 fixture 跑出各階段的數字。

### M2：基準

- 在真實的 Figma 上量小（約 40 層）、中（約 200 到 300 層）、大（盡量接近 1,000 層）各一個 frame，每個 3 次。
- 寫成相容性紀錄，ROADMAP 寫上數字。不設 CI 門檻。

驗證：同一個 frame 3 次的差異在合理範圍內；和 2026-10-01 的數字對照。

### M3：減少等待

依 M2 的數字決定先做哪幾項。目前看得到的候選：

- 隱藏圖層不等 mirror。
- 判斷屬性面板已換成這一層時，找更直接的訊號取代等滿 400 或 500 ms，例如面板的 DOM 停止變化。
- 截圖時等縮放提示消失的時間。
- M2 量出來的其他大項。

每一項都要符合兩個條件：同一個 frame 改動前後各拍一次，快照內容完全相同（比較結果 0 變更）；M2 的數字確實下降。

驗證：單元測試、整合測試、登入版 canary（先問使用者）、前後快照比較。

### M4：增量快照研究（關卡）

要回答的問題：不逐層選取，能不能知道哪些圖層的屬性變了。

- 候選訊號是每次快照本來就有的截圖：和上一次的截圖逐像素比較，把變動的區域對到上一次快照中各圖層的位置，只重讀這些圖層，再加上走訪看得到的結構變化（新增、移除、移動、改名、隱藏）。
- 實驗：
  1. 沒有變動時，同一個 frame 的兩次截圖是否完全相同；不相同的話，雜訊有多大。
  2. 使用者在自己的檔案做幾種已知的修改，例如顏色、差 1 px 的間距、文字樣式、隱藏圖層、匯出設定、元件屬性，看哪些在截圖上看得出來，又要多大的縮放比例才看得出來。
- 看不出來的修改，例如匯出設定、被蓋住的圖層、縮小後只差 1 px 的地方，就是增量快照會漏掉的部分。
- 結果寫成紀錄，交給使用者決定要做 M5、縮小範圍，還是不做。只記數字與修改種類，不記圖層名稱。

### M5：增量快照（M4 通過才做）

- 再拍同一個 root 時，只重讀變動區域內與結構有變化的圖層。結果標明哪些重讀、哪些沿用上一次，以及哪些種類的修改看不出來。`refresh: true` 仍然完整重讀。
- 細節等 M4 有結果後另外寫。

### M6：文件與發版

- 更新 `docs/mcp-tools.md`、README 的工具表、CHANGELOG、ROADMAP 與相容性紀錄，發 0.7.0。

## 使用者的決定，2026-10-12

1. 基準在兩個地方量：小型 frame 用登入版 canary 腳本反覆跑；中型（200 到 300 層）用私人測試檔，到時請使用者在 Arc 打開分頁。
2. v0.7.0 期間，登入版 canary 帳號可以超出原本「一天最多一次、少量圖層」的用量來跑基準。只讀使用者自己的公開檔，不改動任何東西。
3. 增量快照研究用公開的 canary 檔，由使用者做修改、事後還原；canary 腳本讀得到，所以實驗可以自動化。

## 風險

| 風險 | 緩解 |
|---|---|
| 等待縮短後，讀到的是前一個圖層的屬性面板 | 每項改動都比較前後的快照內容，必須 0 變更；發版前跑登入版 canary |
| 量測受網路與電腦負載影響 | 每個 frame 跑 3 次取中位數，固定同一台電腦 |
| 截圖比較的雜訊大到每次都判斷為有變動 | M4 先量雜訊再決定門檻，行不通就停在 M4 |
| 增量快照漏掉看不出來的修改，agent 用了過時的值 | 結果列出沿用的圖層與看不出來的修改種類；`refresh: true` 完整重讀 |
| 大型 frame 接近一次 3 分鐘的上限 | 快照已可分次續讀；基準會記下大型 frame 分成幾次 |

## M1 結果，2026-10-12

### 做了什麼

- extension 的 `Timings`（`apps/extension/src/timings.ts`）累計各階段的毫秒數與慢路徑的次數；分頁、背景與截圖三段合併後，放在快照結果的選填欄位 `timings`。伺服器寫在 `snapshot_layer` 那行 log 的最後，不放進工具結果。`PROTOCOL_VERSION` 不變。
- `waitForPanel` 回報它怎麼判斷屬性面板已換層：標題與內容都換了、只有內容換了（等滿 500 ms）、或只有標題對上（等滿 400 ms）。
- `pnpm bench:snapshot`（`tests/bench/snapshot.mjs`）：預設用登入版 canary 的 profile；`--attach` 改用使用者自己的瀏覽器與設定，啟動的伺服器會接手 port，使用者的 agent 工作階段下一次呼叫時會接回去。
- 測試：`waitForPanel` 三種判斷與 `Timings` 合併的單元測試；伺服器 log 帶有計時、而且沒有圖層名稱的測試。MCP 155 項、extension 207 項、protocol 18 項全部通過。

### 發現：canary profile 一直跑舊的 background

- Chrome 會把擴充功能的 service worker 留在 profile 裡，版本號沒變就不重新讀取磁碟上的檔案，即使重新建置過。`~/.figloo/canary-profile` 的快取停在 10-07 11:07，所以從那之後登入版 canary 跑的都是當時的 background；content script 每次都是新的。
- 影響：10-07 的 background 拆分（4790e37）與 `missingAnchors` 的轉送（9797836）沒有被登入版 canary 驗到，其中「沒有缺少的 UI 錨點」那一項因為欄位不存在而落空通過。訪客版的整合測試每次用新的 profile，CI 也是，所以這些 background 的改動仍有被測到。
- 以 `chrome.runtime.reload()` 重新載入，擴充功能會被停用（以命令列載入的擴充功能不能這樣重新載入）。改為每次啟動前刪掉 profile 裡的 `Default/Service Worker`（使用者同意），登入狀態不受影響。修正後登入版 canary 通過，21 秒。
