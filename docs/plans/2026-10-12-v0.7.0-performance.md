# v0.7.0：效能

日期：2026-10-12
狀態：M1 完成（ad061bf）；M2 完成（f4a970d）；M3 完成（eaee200、2d9c7c3）；M4 完成（2026-10-12）；M5 不做（使用者決定）；變數完成（2026-10-12）；下一步 M6
依據：[產品化計畫](2026-10-06-productization-and-reliability.md)第 4.9 節、第 4.10 節的 Performance 基準與 v0.7.0；[ROADMAP](../../ROADMAP.md) 的 0.7.0

## 目標

拍快照變快，而且快多少有數字。再拍同一個畫面時只重讀有變動的部分，前提是找得到不必逐層選取就能看出屬性變動的訊號，也就是產品化計畫第 4.9 節的關卡。

## 現況

- 已知的數字都來自 2026-10-01：278 層 34.7 到 38.8 秒，其中截圖 3.5 秒、走訪 4.5 到 5.6 秒，其餘是逐層讀取，每層約 0.11 秒；198 層 28.8 秒。之後加了分組標題、parse guard 與背景暫停，沒有重新量過。
- 伺服器的 log 只記總時間、走訪時間與 UI 操作次數。截圖與逐層讀取內部的各個步驟沒有分開計時。
- 逐層讀取時，每一層的步驟是：在圖層面板找到那一列（必要時捲動）、點選並等 Figma 標示選取、等屬性面板換成這一層、解析屬性面板與匯出區塊、等 mirror 標出位置。
- 從程式看得到的固定等待：
  - 屬性面板內容變了、但標題不是圖層名稱時（例如圖片顯示檔名），等滿 500 ms；標題是圖層名稱、但內容沒變時（相鄰兩層長得一樣），等滿 400 ms。
  - 非文字圖層的位置 mirror 還沒標出時，最多等 300 ms。mirror 從來不標隱藏圖層，所以每個隱藏圖層都等滿 300 ms，而走訪結束時就已經知道哪些圖層是隱藏的。
  - 截圖：縮放後等 500 ms 動畫，再等 200 ms，然後等縮放提示消失，最多 4 秒，實測約 3 秒。
- 快照已有 24 小時的快取（`snapshotTtlHours`）與 `refresh`。再拍同一個 root 時會和上一次比較，標出新增、變更與移除的圖層，但仍是整個重讀。

## 里程碑

每個里程碑完成後先不 commit，回報結果，等使用者同意後再 commit 並 push。

### M1：分段計時

- extension 在快照結果加上各階段的時間：截圖（縮放、等提示消失）、走訪、逐層讀取各步驟的總和、等滿 400 ms、500 ms 與 300 ms 的次數、收回展開的圖層與還原畫面。只有數字，沒有圖層名稱或 ref。
- 伺服器把它寫進 log，不放進 agent 看到的工具結果。協定只加選填欄位，不改 `PROTOCOL_VERSION`。
- 新增 `pnpm bench:snapshot`：用登入版 canary 的 profile，對設定的幾個 frame 以 `refresh: true` 各拍 N 次，列出各階段的中位數。

驗證：計時累計的單元測試；整合測試的 fixture 跑出各階段的數字。

### M2：基準

- 在真實的 Figma 上量小（約 40 層）、中（約 200 到 300 層）、大（盡量接近 1,000 層）各一個 frame，每個 3 次。
- 寫成相容性紀錄，ROADMAP 寫上數字。不設 CI 門檻。

驗證：同一個 frame 3 次的差異在合理範圍內；和 2026-10-01 的數字對照。

### M3：減少等待

依 M2 的數字決定先做哪幾項。目前看得到的候選：

- 隱藏圖層不等 mirror。
- 判斷屬性面板已換成這一層時，找更直接的訊號取代等滿 400 或 500 ms，例如面板的 DOM 停止變化。
- 截圖時等縮放提示消失的時間。
- M2 量出來的其他大項。

每一項都要符合兩個條件：同一個 frame 改動前後各拍一次，快照內容完全相同（比較結果 0 變更）；M2 的數字確實下降。

驗證：單元測試、整合測試、登入版 canary（先問使用者）、前後快照比較。

### M4：增量快照研究（關卡）

要回答的問題：不逐層選取，能不能知道哪些圖層的屬性變了。

- 候選訊號是每次快照本來就有的截圖：和上一次的截圖逐像素比較，把變動的區域對到上一次快照中各圖層的位置，只重讀這些圖層，再加上走訪看得到的結構變化（新增、移除、移動、改名、隱藏）。
- 實驗：
  1. 沒有變動時，同一個 frame 的兩次截圖是否完全相同；不相同的話，雜訊有多大。
  2. 使用者在自己的檔案做幾種已知的修改，例如顏色、差 1 px 的間距、文字樣式、隱藏圖層、匯出設定、元件屬性，看哪些在截圖上看得出來，又要多大的縮放比例才看得出來。
- 看不出來的修改，例如匯出設定、被蓋住的圖層、縮小後只差 1 px 的地方，就是增量快照會漏掉的部分。
- 結果寫成紀錄，交給使用者決定要做 M5、縮小範圍，還是不做。只記數字與修改種類，不記圖層名稱。

### M5：增量快照（M4 通過才做）

- 再拍同一個 root 時，只重讀變動區域內與結構有變化的圖層。結果標明哪些重讀、哪些沿用上一次，以及哪些種類的修改看不出來。`refresh: true` 仍然完整重讀。
- 細節等 M4 有結果後另外寫。

### M6：文件與發版

- 更新 `docs/mcp-tools.md`、README 的工具表、CHANGELOG、ROADMAP 與相容性紀錄，發 0.7.0。

## 使用者的決定，2026-10-12

1. 基準在兩個地方量：小型 frame 用登入版 canary 腳本反覆跑；中型（200 到 300 層）用私人測試檔，到時請使用者在 Arc 打開分頁。
2. v0.7.0 期間，登入版 canary 帳號可以超出原本「一天最多一次、少量圖層」的用量來跑基準。只讀使用者自己的公開檔，不改動任何東西。
3. 增量快照研究用公開的 canary 檔，由使用者做修改、事後還原；canary 腳本讀得到，所以實驗可以自動化。

## 風險

| 風險 | 緩解 |
|---|---|
| 等待縮短後，讀到的是前一個圖層的屬性面板 | 每項改動都比較前後的快照內容，必須 0 變更；發版前跑登入版 canary |
| 量測受網路與電腦負載影響 | 每個 frame 跑 3 次取中位數，固定同一台電腦 |
| 截圖比較的雜訊大到每次都判斷為有變動 | M4 先量雜訊再決定門檻，行不通就停在 M4 |
| 增量快照漏掉看不出來的修改，agent 用了過時的值 | 結果列出沿用的圖層與看不出來的修改種類；`refresh: true` 完整重讀 |
| 大型 frame 接近一次 3 分鐘的上限 | 快照已可分次續讀；基準會記下大型 frame 分成幾次 |

## M1 結果，2026-10-12

### 做了什麼

- extension 的 `Timings`（`apps/extension/src/timings.ts`）累計各階段的毫秒數與慢路徑的次數；分頁、背景與截圖三段合併後，放在快照結果的選填欄位 `timings`。伺服器寫在 `snapshot_layer` 那行 log 的最後，不放進工具結果。`PROTOCOL_VERSION` 不變。
- `waitForPanel` 回報它怎麼判斷屬性面板已換層：標題與內容都換了、只有內容換了（等滿 500 ms）、或只有標題對上（等滿 400 ms）。
- `pnpm bench:snapshot`（`tests/bench/snapshot.mjs`）：預設用登入版 canary 的 profile；`--attach` 改用使用者自己的瀏覽器與設定，啟動的伺服器會接手 port，使用者的 agent 工作階段下一次呼叫時會接回去。
- 測試：`waitForPanel` 三種判斷與 `Timings` 合併的單元測試；伺服器 log 帶有計時、而且沒有圖層名稱的測試。MCP 155 項、extension 207 項、protocol 18 項全部通過。

### 發現：canary profile 一直跑舊的 background

- Chrome 會把擴充功能的 service worker 留在 profile 裡，版本號沒變就不重新讀取磁碟上的檔案，即使重新建置過。`~/.figloo/canary-profile` 的快取停在 10-07 11:07，所以從那之後登入版 canary 跑的都是當時的 background；content script 每次都是新的。
- 影響：10-07 的 background 拆分（4790e37）與 `missingAnchors` 的轉送（9797836）沒有被登入版 canary 驗到，其中「沒有缺少的 UI 錨點」那一項因為欄位不存在而落空通過。訪客版的整合測試每次用新的 profile，CI 也是，所以這些 background 的改動仍有被測到。
- 以 `chrome.runtime.reload()` 重新載入，擴充功能會被停用（以命令列載入的擴充功能不能這樣重新載入）。改為每次啟動前刪掉 profile 裡的 `Default/Service Worker`（使用者同意），登入狀態不受影響。修正後登入版 canary 通過，21 秒。

## M2 結果，2026-10-12

詳見[快照的效能基準](../compatibility/2026-10-12-snapshot-benchmark.md)。`--attach` 在使用者的 Arc 上可用。使用者選到的畫面是 605 層：75.2 秒，每層 124 ms；每層約 80 ms 的點選與等屬性面板占 66%，走訪的展開與結束時的收回合計約 21 秒，占 28%，相鄰圖層長得一樣而等滿 400 ms 的有 23 次。小型 frame（39、59 層）約 8 到 10 秒，等縮放提示消失的 2.3 秒占 25% 到 30%。沒有中型 frame 的數字。

## M3 進度，2026-10-12

使用者的決定：走訪的展開與結束時的收回都用 Alt-click，接受「收合圖層底下原本展開的內層，收回後變成收合」；第 2 項的實驗用使用者在 canary 檔新增的測試 frame。

### 1. 截圖時不等縮放提示（完成）

- Figma 的提示框（「Zoom to selection」）在視窗底部中央，約 3.0 秒後消失；畫面填滿時常和裁切範圍重疊，所以只檢查重疊省不了多少。
- 改為截圖期間加一條 CSS 隱藏 `[data-testid="visual-bell-root"]`，截完（`finish_capture`）就移除。提示框不在這個元素裡時（Figma 改版），照舊等它消失。
- 驗證：縮放後 0.9 秒與 3.5 秒的畫布截圖逐像素相同，三個 frame 都是，所以提早截圖不會拍到還沒渲染完的畫面；截圖中沒有提示框。單元測試涵蓋隱藏、還原與找不到外框時照舊等待。
- 效果：`capture.toast` 從 2.3 秒降到 0.2 秒（剩下的是按 Esc 之後原有的 200 ms）。`capture` 工具也一樣快了約 2 秒。

### 3. 走訪與收回用 Alt-click（完成）

- 實測 Figma 的圖層面板：Alt-click 收合的圖層會展開它與裡面所有圖層（包括 instance）；Alt-click 展開的圖層會全部收合。
- 走訪遇到收合的圖層時改用 Alt-click，裡面不必再逐層展開；收回時對這些圖層再 Alt-click 一次。instance 的內容照舊跳過。
- 驗證：
  - 舊版與新版走訪對 0:2 與 0:78 拍出的快照逐字元相同。
  - root 原本收合、以及 root 與一個子層原本展開兩種情況，快照後畫面上的展開狀態都和原本相同。
  - 單元測試涵蓋一次展開、一次收回，以及收合圖層底下原本展開的內層會變成收合。
- 效果（canary，3 次中位數）：0:2 走訪 0.47 → 0.05 秒、收回 0.49 → 0.09 秒，總時間 7.8 → 5.0 秒；0:78 走訪 0.57 → 0.09 秒、收回 0.64 → 0.09 秒，總時間 9.6 → 6.6 秒（含第 1 項）。

### 2. 屬性相同的相鄰圖層（完成）

- 使用者在 canary 檔新增測試 frame `Figloo test`（302:397）：4 個以 Cmd+D 複製的矩形，以及 3 個同名的文字圖層。Cmd+D 會遞增名稱，所以矩形叫 Rectangle 22 到 25。
- 實驗：每次切換，屬性面板的標題與各區段（含匯出區段）都在圖層列被選取的同一刻更新；之前看到約 100 ms 後的第二次變動，是 `inspect_nodes` 讀完後還原選取。屬性相同、名稱不同的圖層之間切換時，只有標題改變；名稱與屬性都相同時，面板完全沒有變動，沒有可用的訊號。
- 改動：
  - 判斷面板換層的指紋加入標題，所以屬性相同、名稱不同的圖層（例如複製出來的）不再等滿 400 ms。名稱與屬性都相同的仍等 400 ms。
  - 快照讀 root 時，如果使用者原本就只選了這個 root，面板已經顯示它，不再等待；使用者通常就是選著要拍的畫面。
- 驗證：只差這兩處的新舊版本，對 302:397、0:2、0:78 拍出的快照逐字元相同；302:397 等滿 400 ms 的次數 5 → 2，等屬性面板 2.1 → 0.9 秒；0:2 的 1 次也沒有了。

### 截圖裁切的 bug（順便修正）

- 0:627 與 302:397 的快照會回報 `UI_NOT_READY`（截圖沒有涵蓋整個 root），`capture` 則默默裁偏。原因：Shift+2 之後，mirror 有時把 frame 放在離實際畫面 141 px 的地方，直到選取改變才更新；快照讀取時重新選取 root，拿到的是正確位置，所以兩者對不上。
- 曾試過「Shift+2 一定把圖層水平置中」的判斷，但 0:78 有超出 frame 的橫向輪播，Figma 是把整體置中，frame 本身不在中間，這個判斷不成立，已放棄。
- 改為縮放後一律按 Esc 再重新選取一次，採用 mirror 新給的位置；快照另外在 root 落在裁切範圍外、但已和截圖確認時，依確認的位置從完整截圖重新裁切。每次多約 0.13 秒。
- 驗證：依原本會失敗的順序拍 302:397、0:627、0:2、0:627、0:78、302:397，全部成功，root 在截圖中都留 12 px 邊距；`capture` 的 0:627 與 0:78 檢視過，裁切正確。

### 4. 還原畫面（不做）

- 每一輪都要等 mirror 顯示新畫面，約 0.5 秒，這是下限。Arc 上 605 層的畫面一輪就還原（0.54 秒）；只有 headless 的 0:78 用了三輪（1.7 秒）。可省的時間少，先不做。

### 結果

在 Arc 上重量 605 層的畫面：75.2 秒 → 39.8 秒（-47%），等滿 400 ms 的次數 23 → 0，走訪 10.9 → 0.6 秒，收回 10.2 → 0.1 秒。剩下的 90% 是逐層點選與等屬性面板。詳見[快照的效能基準](../compatibility/2026-10-12-snapshot-benchmark.md)的「M3 之後」。README、skill 與工具說明中的「300 層約 40 秒」在 M6 依新數字更新。

## M4 結果，2026-10-12

詳見[增量快照研究](../compatibility/2026-10-12-incremental-snapshot-research.md)。

- 沒有修改時：純色與文字的畫面，截圖位元組相同；圖片多、縮放小的畫面有圖片載入造成的大範圍差異。其他人的選取框也會出現在截圖中。
- 使用者做的 5 個修改，快照逐層比對全部抓到；截圖單獨看得出來的最多 2 個（字重，以及應該可以的 1 px 移動）。極小的色差、被蓋住的圖層與匯出設定看不出來。
- 建議：不做 M5。看不出來的正好是實作依賴的精確值，漏掉時不會有任何提示；M3 之後完整的快照已快了將近一半。

## 新增的里程碑：變數（使用者決定，2026-10-12）

M4 的準備中發現，綁了 Figma 變數的顏色 Figloo 讀不懂（`unreadable: colors`）。使用者選擇在 v0.7.0 一起處理：

- 讀出綁了變數的顏色：hex、透明度，以及變數名稱。
- 檢查間距、圓角、字級等數字變數在屬性面板的樣子，有同樣問題就一起處理。
- `summarize_snapshot` 與 `map_tokens` 帶出變數名稱；`map_tokens` 先依變數名稱對應專案的 token。

## 變數的結果，2026-10-12

詳見[綁定 Figma 變數的值](../compatibility/2026-10-12-variables.md)。綁了變數的顏色從讀不懂改為讀出 hex 與變數名稱；綁了變數的數字從讀成變數名稱改為讀出代表的值與變數名稱。`summarize_snapshot` 把綁與不綁變數的同一個值分開列出，`map_tokens` 把名稱像變數的 token 排第一。字級等文字樣式的變數、多個 mode 與透明度沒有實測。
