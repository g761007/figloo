# 頁面地圖與快照：實作前的企劃與研究

日期：2026-10-01  
狀態：研究完成；實作計畫在 2026-10-01 review 後調整，並經使用者確認；第一階段完成，見[驗證紀錄](../compatibility/2026-10-01-page-snapshot-phase1.md)；第二階段完成，以單元測試驗證；第三階段待開始  
依據：使用者提出的情境，以及 2026-10-01 在 Arc 上的實測

## 使用情境

工程師打開設計稿，找到要實作的頁面，選取這頁的 root 元件，告訴 agent「我要做這頁」。Figloo 自動截取這頁的畫面，並提供所有子元件的地圖，不含屬性細節。之後 agent 需要某個元件的屬性時，依地圖直接定位並查詢；也可以搭配相鄰元件與多層展開，一次多拿一些參數，減少呼叫次數。

## 目標與非目標

目標：

- 一次呼叫取得頁面截圖與整棵子樹的結構地圖。
- 地圖中的 ref 可以直接用來讀取屬性、找相鄰元件與匯出，不必再逐層探索。
- 減少 agent 的呼叫次數與等待時間。

非目標：

- 不展開 instance 內部；需要時再即時查詢。
- 不在背景自動掃描。快照只在使用者或 agent 明確要求時產生，範圍限於選取的 root。

原本的非目標「不預先讀取所有屬性」已依使用者的決定取消：快照一次讀取所有屬性並存成檔案，之後的查詢不再操作 Figma。

## 研究結果

對象：使用者提供的私人測試檔中，一個手機畫面的 frame「測試畫面」。Instance 視為一個整體，不展開內部。

| 項目 | 結果 |
|---|---|
| 圖層數 | 197，其中 instance 45 個 |
| 最大深度 | 6 層；各層依序為 12、28、30、94、23、10 個 |
| 類型 | Instance 45、Text 39、Auto layout 30、Group 26、Rectangle 17、Image 16，其他 24 |
| 自動命名的圖層 | 82 個，約 42%，例如 Group 908、Frame 882、Rectangle 388 |
| 精簡大綱的大小 | 每個圖層一行縮排、ref、類型與名稱，共 6,773 bytes |
| 以現有工具逐層走完 | 64 次列舉、480 次 UI 操作、16.5 秒；結束後面板恢復原狀 |
| 連 instance 內部一起走 | 走到 101 個圖層、8 秒時，找回 instance 內部的圖層失敗 |
| 第一層 12 個子層的位置 | 以相鄰元件的量測約 0.5 秒，數值與屬性面板一致 |

由結果得出的判斷：

1. 地圖的大小不是問題。依這頁的密度，每次 32 KiB 的輸出上限約可容納九百個圖層。
2. 耗時是主要問題。現有工具每列舉一層就收合一次，下一層又要重新展開祖先。專用的走訪可以一次展開、一次讀完、最後收回，UI 操作與耗時應該大幅下降，但要以原型實測。
3. Instance 內部應按需查詢。內部的 ID 只在單次頁面載入有效，深入走訪既慢又不穩定。
4. 只靠名稱不足以定位。超過四成是自動命名，必須讓 agent 能把截圖上的位置對應到圖層。

## 放寬限制後的評估：一次取得整棵子樹的所有內容

使用者在 2026-10-01 決定放寬原本「只透過 DOM 與網頁介面」的限制，先研究能否一次取得指定 root 與其子樹的所有內容。

### 官方管道與檢視權限

| 管道 | 一次能取得的內容 | View 或 Collab 席位 | Dev 或 Full 席位 |
|---|---|---|---|
| REST API 的 GET file nodes | 整棵子樹的所有屬性 | Tier 1，每月最多 20 次，實際可能更低；依檔案所屬的方案計算 | 付費方案每分鐘 10 到 20 次 |
| 官方 MCP 伺服器 | 結構、程式碼脈絡、截圖 | 付費方案每月最多 6 次工具呼叫 | 每天 200 到 600 次 |
| Plugin | 整份文件 | 不能執行 | Dev Mode 中可執行唯讀 plugin |

結論：

- 只有檢視權限的工程師，透過官方管道每月只有個位數到二十次的額度，只夠偶爾使用。
- 若組織能提供 Dev 席位，官方 MCP 與 REST API 都能直接滿足「一次取得整棵子樹」。
- 繞過 Figma 席位與權限限制的做法，例如讀取內部物件或記憶體，不列入選項。

### 只靠介面完整讀取的實測

2026-10-01，Arc，frame「測試畫面」，instance 視為一個整體：

| 項目 | 結果 |
|---|---|
| 圖層數 | 198 |
| 讀取全部圖層的屬性面板 | 45 秒，每個圖層約 0.23 秒，715 次 UI 操作；每批結束都還原了選取 |
| 屬性資料 | 約 152 KB |
| 走完整棵子樹 | 16.5 秒；使用者展開許多其他圖層時增加到 111 秒 |

結論：只靠介面也能一次取得整頁所有屬性，不受額度限制，但要一到兩分半鐘，期間選取會快速切換、使用者不能操作 Figma。改成一次展開、一次讀完的走訪後，走訪時間應可大幅縮短，總時間估計約一分鐘，要以原型確認。

### 使用者的席位

使用者回覆：團隊成員都是免費席位，沒有付費。因此 REST API 與官方 MCP 每月只有約 6 到 20 次，只夠偶爾核對，不能作為日常開發的主要管道。主要路線改為只靠介面完整讀取，並快取結果。

### 一次展開的走訪原型

研究用腳本，2026-10-01，Arc，同一個 frame；當時使用者另外展開了其他 frame 的許多圖層：

| 走訪方式 | 圖層數 | UI 操作 | 耗時 |
|---|---|---|---|
| 現有工具逐層列舉 | 197 | 480 次 | 16.5 秒；面板很長時 111 秒 |
| 一次展開、一次讀完 | 197 | 138 次 | 約 7 秒，其中走訪 4.0 秒、收回 2.9 秒 |

原型由 root 往下依序讀圖層列，遇到收合且不是 instance 的圖層就展開，讀完再依相反順序只收回自己展開的 64 個圖層。結束後使用者的選取與自己展開的圖層都沒變。

照這個數字，整頁的結構約 7 秒，加上讀取全部屬性面板約 45 秒，一次取得所有內容約 1 分鐘。

### 建議的方向

1. 預設：以介面完整讀取，產生頁面的快照並快取在 MCP 伺服器。之後 agent 的屬性查詢直接從快取回答，不再操作 Figma。
2. 選用：使用者提供自己的 Figma token 時，改用 REST API 一次取得，數秒內完成且數值精確，但每次都會用掉額度。截圖仍用 Figloo 的截圖，不呼叫 GET image，以免額度更快用完。
3. 若組織能提供 Dev 席位，建議直接搭配官方 MCP，額度足夠日常使用。

依使用者的決定，實作計畫只包含第 1 項。

## 使用者的決定，2026-10-01

1. 完整快照約 1 分鐘、期間不能操作 Figma，可以接受。
2. 快照寫成檔案，但不放在專案裡；檔案有有效期限，使用者提醒設計稿有更新時就重新抓取。
3. 不用 REST API 比對資料品質。
4. 團隊都是免費席位，所以主要路線是只靠介面完整讀取。
5. Review 後的實作計畫可以開始；快照上限為 400 個圖層、180 秒。

## 早期選項的處理

| 早期選項 | 處理 |
|---|---|
| `map_layer`：只回傳截圖與大綱 | 改為 `snapshot_layer`：同時讀取屬性與位置，存成快照 |
| 擴充 `get_neighbors` | 不採用：每個圖層的 JSON 摘要約 250 bytes，太大，也不適合閱讀 |
| 只量第一、二層的位置 | 改為每個圖層都記錄位置，讀屬性時一併量測 |
| 截圖上的編號框 | 延後；先以大綱中的位置，加上 root 在截圖中的位置與比例來對應 |
| 釘選頁面 | 延後；快照存成檔案，頁面重新整理後仍可查詢 |
| 放寬 `inspect_nodes` 的上限，或依類型批次讀取 | 上限維持 5 個；批次需求改由 `query_snapshot` 的篩選滿足 |
| Instance | 視為一個整體；需要內部時，用 `get_neighbors` 即時查詢 |
| 觸發方式 | Agent 呼叫 `get_anchor` 後呼叫 `snapshot_layer`；popup 在選取 frame 時提供「我要實作這頁」的提示 |
| 快照只放記憶體，或寫進專案 | 寫成檔案，放在專案外的 `~/.figloo/snapshots/` |

## 2026-10-01 review 的調整

1. 讀取時間遠超過現有工具的 15 秒預算，補上專屬的時間與圖層上限，並核對 service worker、MCP 與 agent 端的逾時。
2. 補上位置的換算方式：先縮放到 root 再量測，截圖附上 root 在圖中的位置與比例。
3. `query_snapshot` 改以 snapshot id 查詢，不需要 Figma 分頁；加入 `under` 篩選與分頁，取代「依類型批次讀取」。
4. 補上檔案細節：root 必須在 instance 之外、檔名把冒號換成連字號、格式版本、清理過期的檔案。
5. 新增研究項目：隱藏圖層的標示。新增選用項目：設計師設定的匯出格式。
6. 修正非目標中與快照矛盾的「不預先讀取所有屬性」，並移除已被取代的早期草案。

## 實作計畫

### 快照的內容

一次讀取使用者指定的 root 與整棵子樹，instance 視為一個整體：

| 內容 | 來源 |
|---|---|
| 結構：每個圖層的 ref、名稱、類型、父層、深度與在同層中的順序；instance 註明有沒有子層 | 一次展開的走訪 |
| 屬性：屬性面板顯示的全部內容，與 `inspect_nodes` 相同，包含文字圖層的文字內容 | 逐一選取每個圖層 |
| 位置與大小：相對 root 的設計稿座標，並註明來源 | 選取時同時讀取 mirror DOM 與屬性面板，見「位置的換算」 |
| 截圖，以及 root 在截圖中的位置與比例 | 讀取前以 `capture` 的流程截取 root |
| 隱藏圖層的標示 | 第一階段研究圖層列有沒有可靠的訊號；沒有就列為限制 |
| 設計師設定的匯出格式（選用） | 屬性面板的匯出區塊；它在切換選取後可能延遲更新，能穩定讀到才加入 |
| 格式版本、建立與到期時間、圖層數、耗時 | MCP 伺服器 |

### 讀取流程

1. 截圖：沿用 `capture` 的流程縮放到 root（Shift+2）並截圖，另外回傳裁切範圍。之後不再移動畫面，位置與截圖使用同一個畫面座標。
2. 選取 root，量測 root 的畫面位置與縮放比例；縮放比例是 root 的畫面寬度除以屬性面板的寬度。
3. 一次展開的走訪：由 root 往下依序讀圖層列，展開收合中且不是 instance 的圖層。
4. 依圖層面板的順序逐一選取每個圖層，讀取屬性面板與 mirror。第 3 與第 4 步能不能合併成一次走訪，第一階段依實測決定。
5. 收回自己展開的圖層，還原使用者的選取與面板的捲動位置。畫面維持縮放在 root，與 `capture` 相同。

### 預算與上限

- 圖層上限 400 個，約兩分鐘。走訪時超過上限就停止，回報子樹過大，並列出 root 的直接子層，請 agent 改選範圍較小的 root。
- 時間上限 180 秒，UI 操作上限依圖層數另訂；兩者都低於 Chrome 對單一 extension 請求的 5 分鐘限制。
- Service worker：現有每 20 秒一次的 heartbeat 經 WebSocket 傳送，Chrome 116 起會重設 30 秒的閒置計時，長時間的請求不會因閒置被終止。
- MCP 端：這個 bridge 請求另訂逾時，例如 200 秒；其他操作維持 20 秒。
- Agent 端：Claude Code 未設定 `MCP_TOOL_TIMEOUT` 時預設 28 小時，不受影響。Codex 每次工具呼叫預設 60 秒，README 註明要為 figloo 設定 `tool_timeout_sec`，例如 300。不做分段輪詢，維持一次呼叫完成。
- 讀取期間，同一個分頁的其他 Figloo 操作回傳 `BUSY`。

### 中止與還原

- 使用者在 Figma 中點擊、按鍵或捲動就中止，沿用現有的偵測；工具說明告知要停止時在 Figma 點一下即可。
- Figma 分頁切到背景也會中止，與現有工具相同。
- 中止時不留下不完整的快照，並盡量收回展開的圖層；使用者已經接手時，以使用者的操作為準。

### 位置的換算

| 情況 | 換算 | 來源標示 |
|---|---|---|
| mirror 有這個圖層 | (圖層的畫面位置 − root 的畫面位置) ÷ 縮放比例；大小同樣除以縮放比例 | `mirror` |
| 文字圖層，或沒有 mirror | 屬性面板的 Top 與 Left 相對最近的 frame（群組不算），加上該 frame 已求得的位置 | `panel` |
| 面板不顯示位置：由 auto layout 決定位置的文字，以及沒有 mirror 時的 auto layout 子層 | 只記大小 | `unknown` |

第一階段要確認：從圖層面板選取不會移動畫面；縮放到 root 後，mirror 能量到 root 內所有非文字圖層。

### 檔案

- 位置：`~/.figloo/snapshots/<檔案 key>/<root ref>.json`，截圖為同名的 `.jpg`。ref 中的冒號換成連字號，避免 Windows 不接受的檔名。資料夾權限 700、檔案 600。
- Root 必須在 instance 之外：instance 內部的 ref 只在單次頁面載入有效，快照無法重用，所以直接回報錯誤。
- 檔案帶格式版本，版本不符時視為沒有快照。
- 有效期限：預設 24 小時，可在 `~/.figloo/config.json` 調整。過期的快照不再使用。
- 寫入新快照時，順便刪除同一個檔案 key 底下已過期的快照。
- 重新抓取：`snapshot_layer` 接受 `refresh`；使用者說設計稿有更新時，agent 就重新抓取。

### MCP 工具

| 工具 | 用途 |
|---|---|
| `snapshot_layer(contextId, ref, refresh?)` | 有未過期的快照就直接回傳，不操作 Figma；否則截圖、讀取並存檔。回傳截圖、snapshot id、建立與到期時間、root 在截圖中的位置與比例，以及精簡大綱：每個圖層一行，包含縮排、ref、類型、名稱、位置與大小，文字圖層附文字內容的開頭，instance 與隱藏圖層加註。這頁約 10 KB；超過 32 KiB 時截斷，並說明改用 `query_snapshot` 的 `under` 查詢其餘部分。 |
| `query_snapshot(snapshot, refs?, text?, type?, under?, details?, cursor?)` | 只讀快照檔，不需要 Figma 分頁或 context，頁面重新整理後也能用。`refs` 回傳完整屬性，每次最多 20 個。`text`（比對名稱與文字內容）、`type`、`under`（限定在某個圖層底下）可以組合篩選，結果以大綱行分頁；加上 `details` 則回傳完整屬性，每頁筆數較少。快照過期時回報錯誤，請 agent 以 `snapshot_layer` 重新抓取。 |

### 其他預設

- Popup：使用者選取 frame 時，複製的提示改成「我要實作這頁」的版本，請 agent 先呼叫 `snapshot_layer`。
- 截圖上的編號框、釘選頁面：延後，等快照用過再評估。
- `inspect_nodes` 的上限維持 5 個；大量讀取改用快照。

### 階段與驗證

| 階段 | 內容 | 驗證 |
|---|---|---|
| 1 | Adapter：讀取的 bridge 操作（走訪、逐一讀取屬性與位置、收回與還原）、專屬的時間與圖層上限、`capture` 回傳裁切範圍；研究隱藏圖層的訊號，以及匯出格式能否穩定讀取 | 單元測試；在 Arc 上讀取測試畫面：屬性與 `inspect_nodes` 抽樣比對、位置與屬性面板抽樣比對、量測總時間；讀取中在 Figma 點一下能中止並還原 |
| 2 | MCP：快照檔、有效期限與清理、`snapshot_layer`、`query_snapshot`、重新產生工具文件 | 單元測試：過期、refresh、版本不符、搜尋與分頁、`under`、檔名轉換、檔案權限 |
| 3 | Popup 提示、README 與相容性文件（含 Codex 的逾時設定）、以 Claude Code 實際用一頁 | 整合測試與 Arc 實測 |

每個階段完成後，經使用者同意再 commit。

### 第一階段的結果

- 278 個圖層的 frame 在 39 秒內讀完，不到原本估計的一分鐘。
- 第 3 與第 4 步不合併：走訪只占 16% 的時間，分開走訪還能在逐一讀取前先知道子樹是否過大。
- 隱藏圖層：圖層列有可靠的訊號，快照加上 `hidden`。Mirror 仍然會給隱藏圖層位置。
- 匯出格式：等屬性面板確認切換後就能穩定讀到，快照加上 `exports`。
- 時間上限的 180 秒中保留 15 秒，給逾時後的收回與還原選取。
- 使用者中止時，收回展開的圖層，但保留使用者的選取。

### 第二階段的結果

- `snapshot_layer` 與 `query_snapshot` 依上面的設計完成；snapshot id 的格式是 `<檔案 key>/<root ref，冒號換成連字號>`，例如 `AbCd/570-14192`，直接對應到檔案路徑。
- 大綱的每一行依序是縮排、ref、類型、名稱、`x,y`、`寬×高`；文字內容與名稱不同時附上開頭，最後是 `[hidden]`、`[has layers]`（有子層的 instance）、`[export PNG 2x]` 等標記。大綱放不下時附上 `nextCursor`，交給 `query_snapshot` 接著讀。
- 子樹過大時回報 `SUBTREE_TOO_LARGE`，訊息中列出 root 的直接子層，這些 ref 可以直接用來呼叫 `snapshot_layer`。快照中的 ref 也都加入 context，可以直接交給 `inspect_nodes` 或 `export_asset`。
- `config.json` 的 `snapshotTtlHours` 調整有效期限；補齊設定檔缺少的欄位時，會保留使用者自己加的設定。
