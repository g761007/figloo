# 多個工作階段：自動交接與身分顯示

日期：2026-10-02  
狀態：已實作，三個階段完成並在 Arc 與真實的 Claude Code 工作階段驗證，見[驗證紀錄](../compatibility/2026-10-02-multi-session-handover.md)  
依據：使用者提出的上線情境，以及 2026-10-01 到 10-02 實測時連接埠被其他工作階段佔用的經驗

## 情境

使用者在瀏覽器同時開著兩個專案的 Figma 分頁，本機同時有多個 Claude Code 工作階段，可能輪流或同時使用 Figloo。使用者接受「一次只服務一個工作階段」，但 extension 必須知道自己正在和哪個工作階段溝通。

## 現況

| 情境 | 目前的行為 |
|---|---|
| 兩個 Figma 分頁 | `get_status` 列出所有分頁，工具以 `tabId` 指定分頁，context 綁定分頁與那次頁面載入，彼此不會混在一起。只有畫面上的分頁能操作。 |
| 多個工作階段 | 每個工作階段各自啟動一個 Figloo MCP，搶連接埠 47129。第一個搶到的獨占，其他工作階段的工具全部回報 `NOT_CONNECTED`，`get_status` 只說連接埠被佔用。 |

實測時遇到的問題：

1. 佔著連接埠的是早已閒置的工作階段，真正要用的工作階段連不上。
2. 伺服器只在啟動時嘗試一次，佔用者結束後，其他工作階段也不會接手。桌面版的工作階段不能用 `/mcp` 重新連線，只能開新的工作階段。
3. Extension 不知道自己連的是哪個工作階段，popup 只顯示「Agent: connected」。
4. 升級後仍在執行的舊工作階段跑的是舊版 MCP，與新版 extension 不相容。

## 目標與非目標

目標：

- 任何時刻只有一個工作階段使用 extension，稱為「持有者」。
- 工作階段呼叫需要 extension 的工具時，自動從閒置的持有者手上接過來。
- 持有者正在工作時不交出，請求的一方收到 `BUSY` 與持有者的名稱。
- Extension 與 agent 都看得到持有者是誰。
- 持有者結束後，其他工作階段自動接手，不必重新啟動。

非目標：

- 多個工作階段同時使用 extension。Figma 只在分頁可見時接受操作，真正的平行使用需要兩個 Figma 視窗並排，價值有限；有快照之後，需要 Figma 的時間也很短。之後真的需要時再評估「extension 同時連多個伺服器」的方案，這次的身分與待命機制屆時沿用。
- 在 popup 裡手動指定工作階段。使用者決定採用自動交接。

## 設計

### 工作階段的身分

每個 MCP 伺服器有一個身分：

| 欄位 | 來源 | 例子 |
|---|---|---|
| `client` | MCP 初始化時 client 回報的名稱，`getClientVersion()` | `claude-code` |
| `project` | `CLAUDE_PROJECT_DIR` 的資料夾名稱，沒有時用工作目錄 | `figloo` |
| `pid` | 伺服器的行程 ID | `17807` |
| `startedAt` | 伺服器啟動的時間 | |
| `serverVersion` | 伺服器版本 | `0.2.0` |

同一個專案開兩個工作階段時，以啟動時間區分，例如「figloo（09:15 啟動）」。

### 持有者與待命

- 伺服器啟動時嘗試監聽 47129。成功就成為持有者；失敗就進入待命。
- 待命的伺服器每 3 秒重試一次。持有者結束或當掉後，第一個重試成功的成為新的持有者，extension 依現有的重新連線機制連上它。
- 持有者不寫鎖定檔，身分透過下面的 HTTP 端點查詢，因此持有者當掉時不會留下過時的紀錄。

### 交接流程

持有者的 HTTP 伺服器（目前對 WebSocket 以外的請求一律回 404）新增兩個端點，都要求 `Authorization: Bearer <配對 token>`：

| 端點 | 用途 |
|---|---|
| `GET /holder` | 回傳持有者的身分、是否忙碌，以及最後一次處理請求的時間 |
| `POST /handover` | 請持有者交出連接埠，內容是請求者的身分 |

待命的伺服器收到需要 extension 的工具呼叫時：

1. 送出 `POST /handover`，最多等 2 秒。
2. 持有者判斷是否忙碌：有請求還在進行，例如快照，或最後一次請求結束、或接手後不到 10 秒，都算忙碌。
   - 忙碌：回 409 與自己的身分，請求者對 agent 回報 `BUSY`：「Figloo 正在為 figloo（Claude Code，09:15 啟動）工作，稍後再試」。
   - 閒置：以 close code 4010（handed over）關閉與 extension 的連線，停止監聽，回 200 並進入待命。
3. 請求者在 2 秒內反覆嘗試監聽 47129，成功後等 extension 連上，最多 5 秒，再執行原本的請求。
4. 其他結果：
   - 連不上：連接埠沒人用，直接監聽。
   - 回 404：持有者是不支援交接的舊版。回報「另一個工作階段執行的是舊版 Figloo，請重新啟動它」。
   - 逾時：持有者沒有回應。回報「持有 Figloo 的工作階段沒有回應，請關閉它」。

10 秒的緩衝避免兩個工作階段搶來搶去：剛接手、正要送出請求的持有者不會立刻被搶走，持續在使用的工作階段也不會被打斷。

Extension 收到 close code 4010 時在 200 ms 後重新連線，不走一般的退避時間，所以交接的總時間約 1 秒。

### 給 agent 的狀態

- `get_status` 的 `bridge` 新增 `role`（`holder` 或 `standby`）與 `holder`（持有者的身分）。
- 待命時的提示：「Figloo 目前服務 figloo（Claude Code，09:15 啟動）。呼叫任何 Figloo 工具就會在它閒置時接手。」
- `get_status` 本身不觸發交接，所以查看狀態不會打斷持有者。

### Extension 的顯示

- 協定的 `welcome` 訊息新增選用的 `session` 欄位，帶上伺服器的身分。舊版伺服器沒有這個欄位時，照舊只顯示「connected」。
- 工具列提示與 popup 的 agent 那一行改成「Agent: Claude Code · figloo（09:15 啟動）」。
- 選項頁面顯示同樣的資訊，以及最近一次交接的時間。

### 兩個 Figma 分頁

不需要改變架構，只補強選擇分頁：

- 有兩個以上可用的分頁時，`get_status` 的提示請 agent 問使用者要用哪個檔案，或使用使用者貼上的提示裡的 `tabId`。
- 工具說明註明：使用者貼上的提示已經指定 `tabId` 時，直接使用。

### 安全

- 交接端點要求配對 token，只有能讀 `~/.figloo/config.json` 的本機程序能觸發。
- 端點只接受沒有 `Origin` 標頭的請求，所以網頁就算猜到 token 也無法觸發。
- 只監聽 127.0.0.1，與現在相同。

### 版本

- 新增功能，套件版本升到 0.2.0。
- `welcome` 的新欄位是選用的，extension 與伺服器之間仍相容，協定版本維持 0.2.0。
- 0.1.0 的伺服器不支援交接。這種伺服器持有連接埠時，新版伺服器會說明「請重新啟動那個工作階段」；0.1.0 的伺服器待命時不會自動接手，要重新啟動才會有新行為。

## 階段與驗證

| 階段 | 內容 | 驗證 |
|---|---|---|
| 1 | MCP：身分、待命與重試、`/holder` 與 `/handover`、請求者的交接流程、`get_status` 的角色與提示 | 單元測試：同一個程序裡啟動兩個伺服器與一個假 extension，驗證閒置時交接、忙碌時回報 `BUSY`、10 秒緩衝、持有者結束後接手、舊版持有者、沒有回應的持有者、錯誤的 token、帶 `Origin` 的請求 |

| 3 | README 與相容性文件、多分頁的提示、在兩個 Claude Code 工作階段實際交接、打包 0.2.0 | 整合測試與 Arc 實測 |

每個階段完成後，經使用者同意再 commit。

## 風險

| 風險 | 緩解 |
|---|---|
| 兩個工作階段持續交替使用，互相搶奪 | 10 秒緩衝；忙碌時回報 `BUSY` 與持有者，由使用者決定先用哪一個 |
| 交接時兩個待命的伺服器同時搶連接埠 | 只有一個能監聽成功；另一個重新向新的持有者請求，此時新持有者在緩衝期內，會回報 `BUSY` |
| 持有者當掉但連接埠尚未釋放 | 作業系統在程序結束時釋放；待命的伺服器每 3 秒重試 |
| Context 在交接後失效 | Context 綁定分頁的頁面載入，與哪個伺服器無關；交回來後仍然有效 |
| Agent 在交接過程中逾時 | 交接最多約 9 秒：請求 2 秒、監聽 2 秒、等 extension 5 秒，在一般操作的 20 秒逾時內 |

## 使用者的決定，2026-10-02

1. 交接的緩衝時間：10 秒。
2. 持有者結束後，由待命的伺服器自動接手。
3. 工作階段的名稱：依提案，以 client、專案資料夾與啟動時間組成，實作後可再調整。
4. 緩衝的計算，第一階段實作後確認：有請求正在進行（含交接與等待 extension），或最後一次請求結束不到 10 秒，就算忙碌。因請求而接手時，交接本身算在那次請求裡；持有者結束、由待命伺服器自動接手時不啟動緩衝，讓真正需要的工作階段能立刻接手。
5. 持有者自己呼叫 `get_status` 時會向 extension 更新分頁，也算一次請求。
6. `client` 取 MCP client 回報的 `title`，沒有時用 `name`；Claude Code 回報的 `title` 是「Claude Code」。
7. 第三階段追加：`GET /holder` 也回傳持有者最後收到的分頁清單，待命時的 `get_status` 列出這些分頁（`tabsFresh` 為 false），讓沒有貼上提示的 agent 也有 `tabId` 可用，查詢本身仍不觸發交接。

讀取時的遮罩與切換分頁時的暫停，另見[讀取時的遮罩與暫停](2026-10-02-reading-overlay.md)。
