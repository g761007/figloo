# v0.5.0：可靠性與安裝體驗

日期：2026-10-07
狀態：M1 到 M6 完成（2026-10-07），M7 待與使用者約時間
依據：[產品化計畫](2026-10-06-productization-and-reliability.md)第 4.3、4.4、4.6、4.7 節與第 5 節的 v0.5.0

## 目標

使用者與 agent 不必理解 Figloo 的架構，就能知道哪裡不能用、為什麼、怎麼修。成功條件：把 README 的 Quickstart 貼給全新的 agent 工作階段，能完成安裝與第一次 Design-to-Code。

## 現況

- 工具錯誤已回傳 `{ code, message, hint }`，但 hint 分散在 `exploration.ts`、`snapshot-tools.ts`、`export-asset.ts` 三份表，沒有分類，也沒有機器可讀的「能不能重試」。
- `get_status` 回報每個分頁的 `readiness`、`access` 與五項能力，但沒有說缺了哪一項會影響哪些工具。mirror 缺少時仍是 `READY` 且沒有提示；非英文介面完全沒有提示。
- probe 的 selector 寫在程式裡，沒有清單與可靠度分級；Diagnostics 只顯示五項能力。
- 版本不符時，伺服器只把 protocol 版本寫進 `lastError`，`get_status` 沒有說該更新哪一邊；hello 已經帶 `extensionVersion`。
- CLI 只有 `serve` 與 `pair`，extension 連上之前的問題（Node 版本、設定檔、port 被誰占用）只能靠使用者自己查。

## 里程碑

每個里程碑完成後先不 commit，回報結果，等使用者同意後再 commit 並 push。

### M1：錯誤分類與可否重試（只改 MCP 伺服器）

- 新增 `apps/mcp/src/errors.ts`：每個錯誤碼一筆，含類別（Connection、Compatibility、Context、User Action、Figma UI、Export、Snapshot、Filesystem、Request）、`retryable` 與給 agent 的下一步。三份 hint 表合併進來，沒有 hint 的錯誤碼補上。
- 工具錯誤的回傳加上 `retry` 與 `category`；`docs/mcp-tools.md` 的錯誤碼表加上這兩欄。
- 實作時把布林值的 `retryable` 改成三種值的 `retry`：`yes`（原樣重試可能成功）、`after_user`（使用者照 hint 做完後）、`no`（要先換別的呼叫）。布林值會把「等使用者處理後可重試」和「永遠不行」混在一起。

驗證：單元測試確認 protocol 的每個錯誤碼與伺服器自己的錯誤碼都有一筆；工具錯誤帶出 `retryable`；工具文件重新產生並由既有的一致性測試核對。

### M2：每個分頁的限制與受影響的工具（只改 MCP 伺服器）

- `get_status` 的每個分頁加上 `limitations`：每筆有代碼、受影響的工具、原因與修正方式。涵蓋訪客、編輯權限、介面縮到最小、沒有 screen reader mirror、找不到鍵盤目標、非英文介面，以及 M3 的「Figma 介面認不出來」。
- `hint` 在分頁是 `READY` 但有限制時也提示，例如缺 mirror。

驗證：單元測試涵蓋每種限制的判斷與提示文字；整合測試的訪客分頁要回報訪客限制。

### M3：Figma 介面依賴清單（extension）

- 新增 `apps/extension/src/adapter/anchors.ts`：Figloo 判斷介面可用與否所依賴的錨點，每項標上可靠度（Stable：`data-testid`；Semantic：role 與 aria；Fragile：英文標籤、class、位置），以及是否只在選取圖層後出現。
- probe 依清單檢查不需選取的錨點，回報找不到的錨點名稱（選填欄位，protocol 不升版）；Diagnostics 顯示找不到的錨點。
- 實作時縮小範圍：找不到的錨點只作為資訊回報，因為空白頁沒有圖層列、頁面列表也可能被使用者收起，直接當成限制會誤報。只有「已登入卻找不到右側欄或屬性面板」列為 `UI_CHANGED` 限制，並修正這種情況被誤報成訪客的錯誤訊息。選取後才出現的部分不列入清單，由登入版 canary 以實際使用工具來檢查。
- 登入版 canary 確認沒有找不到的錨點。

驗證：以既有的 fixture 單元測試 probe 與 Diagnostics；整合測試；登入版 canary（先問使用者）。

### M4：版本不符時說清楚該更新哪一邊（只改 MCP 伺服器）

- bridge 拒絕 hello 時記下 extension 的版本與 protocol 版本；`get_status` 的 `hint` 寫出兩邊的套件版本與 protocol 版本，以及該更新 extension 還是伺服器（plugin）。token 不符也一樣記下，並提示重新配對。
- 實作時發現 extension 會在連線關閉時把伺服器的錯誤說明覆蓋成「4001 PROTOCOL_MISMATCH」，選項頁看不出原因；改為保留伺服器的說明，伺服器的說明也寫出兩邊的版本與該更新哪一邊。

驗證：單元測試以假的 extension 送出較舊與較新的 protocol 版本。

### M5：`figloo-mcp doctor`（只改 MCP 伺服器）

- 只檢查 extension 連上之前的事：Node.js 版本、設定資料夾與設定檔是否存在及權限、配對 token、port 是空的、被 Figloo 伺服器占用（列出工作階段與版本、是否有 extension 連著），還是被其他程式占用。不啟動 bridge，不搶 port。
- 輸出逐項的結果與修正方式，有問題時以非零結束碼結束。

驗證：以暫存設定資料夾與假的 holder 單元測試各項檢查；手動執行一次。

### M6：文件與發版

- `docs/agent-install.md` 改為安裝後先跑 `doctor`，再請 agent 呼叫 `get_status` 並依 `limitations` 引導使用者。
- 疑難排解（中英）改為從 `doctor` 與 `get_status` 的檢查出發；相容性 README 補上限制與錨點；CHANGELOG。
- 依版本規則發佈 0.5.0（新增功能，升 minor）。protocol 只加選填欄位，維持 0.3.0。

驗證：全部測試、整合測試、登入版 canary（先問使用者）、release 檢查。

### M7：Quickstart 實測

- 在全新的環境照 README 的 Quickstart 安裝並完成一次 Design-to-Code。需要使用者配合載入 extension 與貼上 token，時間另約。

## 風險

| 風險 | 緩解 |
|---|---|
| 限制判斷太多，`get_status` 變得囉嗦 | 只列實際有的限制，沒有限制時是空陣列 |
| 錨點清單與實際使用的 selector 脫節 | probe 直接讀清單；解析細節仍留在各模組，清單只列判斷可用與否的錨點 |
| 錯誤碼的 retryable 判斷錯誤，agent 一直重試 | 只有確定重試會有不同結果的才標可重試，例如 `BUSY`、`TAB_IN_BACKGROUND`（使用者處理後）；需要使用者動作的標為不可直接重試 |
