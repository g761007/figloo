# 盤點多個 frame：先看全貌，再決定快照哪些畫面

日期：2026-11-24
狀態：使用者已確認（2026-11-24）；M1 完成（a94bd45）；M2 完成（12f37a4）；M3 完成，待 commit；下一步 M4
依據：2026-11-24 的可行性討論，以及同日在使用者提供的私人測試檔上的實測

## 使用情境

全新 App、新功能，或既有 App 的改版，設計稿通常有數十個畫面。工程師想先讓 agent 掌握全貌：有哪些畫面與流程、共用哪些元件、設計師在畫布上寫了哪些規則與 token，以及哪裡做法不一致。agent 做完綜合分析後，提出要快照哪些畫面，經使用者確認才開始快照。

現在只有逐一快照一條路。60 個畫面約 20 分鐘，每個快照回傳的大綱與截圖約 4 到 5k tokens，合計約 250k tokens，會塞滿 agent 的 context。

## 目標與非目標

目標：

- 幾分鐘內盤點使用者指定範圍內的數十個 frame，不逐一選取圖層。
- agent 收到的內容約 10k tokens 等級，不隨圖層數成長；細節存在 MCP 端。
- 盤點結果足以讓 agent 提出快照清單，附上每一項的理由與預估時間。
- 結果存檔，之後的對話或 subagent 不必再讀 Figma。

非目標：

- 不讀屬性面板中的精確數值，例如顏色、字級、間距；那是快照的工作。每個 frame 的尺寸是唯一的例外，見 M2。
- agent 不自行切換 Figma page。
- 不展開 instance 內部。
- 不做跨快照的彙整，也不做快照的精簡回傳；等快照階段的實際用量出來再評估。
- 不自動分群畫面；分群由 agent 依盤點結果判斷。

## 可行性實測，2026-11-24

對象：使用者提供的私人測試檔中，一個有 154 個頂層圖層的 page。Chrome 158，檢視權限，英文 UI。耗時取自 Claude Code 的 MCP 紀錄。

| 操作 | 耗時 | 結果 |
|---|---|---|
| `explore_page` 與 `get_neighbors` 列出 154 個頂層圖層，共 4 次 | 每次 44 到 102 ms | 約 50 KB 的 JSON，每個圖層約 330 bytes，其中 `link` 約 90 bytes |
| 兩個舊畫面往下三層（`depth: 3`） | 各約 1.0 到 1.35 秒，約 31 次 UI 操作 | 47 到 50 個圖層 |
| 一個新畫面往下三層 | 0.4 秒 | 12 個圖層 |
| 整頁截圖 | 約 2 秒 | 982×1568，縮放 5% |
| 單一畫面截圖 | 約 2 秒 | 400×1568，縮放 47%，清楚 |

[快照的效能基準](../compatibility/2026-10-12-snapshot-benchmark.md)中，605 層的畫面在 M3 之後走訪只要 0.6 秒、收回 0.1 秒，其餘約 39 秒都在逐層選取與等屬性面板。所以只走訪、不選取的盤點，每個畫面約 1 秒。

### 頂層圖層的組成

| 類型 | 數量 | 內容 |
|---|---|---|
| Frame | 42 | 大多是畫面，名稱帶流程與狀態，例如「流程 – 子頁 – 無資料狀態」；少數不是畫面，例如捲動區域的示意 |
| Auto layout | 20 | 一部分也是畫面或面板，一部分是散落的小元件 |
| Text | 40 | 設計師的註解：主色與按壓色的色碼和用途、彈窗與底部面板的使用規則、功能說明、待補的畫面 |
| Group | 28 | 草稿元件與素材 |
| Component | 6 | 主元件 |
| 其他 | 18 | 圖片、矩形、向量、instance |

### 發現

1. 畫布上的文字註解幾乎沒有成本，又最能代表設計意圖，例如 token 的色碼與用途、元件的使用規則。圖層面板的名稱就是全文，多行文字也完整。
2. 畫面名稱的品質好，看得出流程與狀態，但分隔符號不統一：` – `、`／`、`/`、`-`、`・`，還有 `@iOS`、`@android` 這類平台後綴。
3. 光看類型分不出畫面：畫面有 Frame 也有 Auto layout，Frame 也不一定是畫面。需要尺寸或縮圖。
4. 畫面內部的名稱，新舊差很多。舊畫面多用 Group，名稱是 Card、Button 這類通用詞，加上自動命名的 `Path 464`、`Ellipse 38`；新畫面用 Auto layout，名稱有語意。
5. 結構看得出同一用途的不同做法：狀態列有三種名稱不同的 instance，頂部導覽至少有四種做法，有一個畫面同時放了兩個導覽。這正是規劃前最需要知道的。
6. 看得出需要人判斷的地方：類型是 Group、名稱卻是元件路徑的圖層（多半是 detach 過的 instance），以及畫面裡貼上的參考截圖（名稱是日期時間的截圖檔名）。
7. 文字圖層的名稱大多是文字內容，但新畫面中有改過名的，這時名稱不是內容。
8. 整頁截圖時每個畫面只剩約 30 px 寬，看不到內容，但看得出畫面排成 8 到 10 排、每排大致是一個流程。畫面大半是空白，裁到內容範圍可以提高解析度。
9. 截圖的既有問題：另一位協作者的游標與名字出現在兩張截圖中，蓋住內容，也有隱私疑慮（[增量快照研究](../compatibility/2026-10-12-incremental-snapshot-research.md)也看過別人的選取框）；「You can only view and comment on this file.」橫幅與底部工具列蓋在畫布上，單一畫面截圖的底部被橫幅擋住一截。快照的截圖也有同樣的問題。

## 設計

### 範圍由使用者決定

| 使用者的做法 | 盤點範圍 |
|---|---|
| 選取幾個 frame | 這些 frame；`get_anchor` 最多回傳 20 個，更多時請使用者改選 section |
| 選取一個或多個 section | section 裡的 frame |
| 什麼都沒選 | 目前 page 的頂層圖層；agent 先列出候選，請使用者確認或刪減 |
| 相關 frame 在其他 page | agent 先問使用者；使用者自己切過去，或說出 page 名稱讓 agent 用 `explore_page` 切換 |

### 新工具 `survey_frames`

參數：

| 參數 | 說明 |
|---|---|
| `contextId` | 來自 `get_anchor` 或 `explore_page` |
| `refs` | 選填。frame 或 section 的 ref；section 換成它裡面的頂層圖層。省略時是 context 所在 page 的所有頂層圖層 |
| `thumbnails` | 選填，預設 false。true 時加上縮圖總覽，見 M3 |

每個 frame 的處理：

1. 走訪：沿用快照的 `walkSubtree` 與 Alt-click，不展開 instance，每個 frame 走完就收回，避免一次展開好幾萬列。每個 frame 的上限與快照相同，2,000 層；超過時只記頂層子圖層，並標明太大。
2. 尺寸：選取 frame 的 root，從屬性面板讀寬高。每個 frame 約 0.1 秒，結束時還原使用者的選取。M2 實測後再決定是否保留。
3. 範圍內的頂層文字圖層視為註解，記下全文。

一次呼叫最多 3 分鐘。沒做完時回傳 `complete: false` 與進度，以相同參數再呼叫就接著做，與 `snapshot_layer` 相同。進行中沿用快照的進度遮罩，按 Stop 或 Esc 就停止。

存檔位置是 `~/.figloo/surveys/<檔案 key>/<survey id>.json`，資料夾權限 700、檔案 600，有效期限沿用 `snapshotTtlHours`。

回傳給 agent 的是精簡的文字，不是每個圖層一個 JSON 物件：

- 畫面清單：每個 frame 一行，包含編號、ref、類型、名稱、寬×高、圖層數、instance 數、文字圖層數、自動命名比例、隱藏圖層數、最常用的 5 個 instance 名稱與次數，以及前 3 段文字的開頭。
- 依名稱分組：把常見的分隔符號視為相同、去掉平台後綴後，依前綴列出各組的 frame 編號。
- 註解：頂層文字圖層的全文與 ref，總長有上限，超過時說明被截斷。
- 元件：每個 instance 名稱用在幾個 frame、共幾次；正規化後（小寫、拆成單字）相同的名稱列在一起，標為「可能是同一用途的不同做法」，交給 agent 判斷。
- 需要人判斷的地方：名稱像元件路徑的 Group 或 Frame、名稱像截圖檔的圖片、自動命名比例高的畫面、太大的 frame。
- 預估快照時間：每個 frame 依圖層數換算，每層約 65 ms，每個 frame 另加約 3 秒。

### 縮圖總覽

`thumbnails: true` 時，對每個 frame 沿用 `capture` 的縮放與裁切，縮成縮圖後在 extension 的 service worker 以 `OffscreenCanvas` 拼成總覽圖，每格標上畫面清單的編號。extension 已經用 `OffscreenCanvas` 裁切與編碼截圖，不需要新套件。

- 每張總覽圖長邊不超過 1568 px，約 3k tokens；每張放幾個畫面，在 M3 依可讀性決定。
- 縮圖與總覽圖都存檔，agent 之後可以只看需要的那張。
- 全部截完才還原使用者的畫面與選取一次。
- 如果逐一縮放的做法有問題，改評估以 JPG 0.5x 匯出 frame。匯出不移動畫面，但會暫時加上匯出設定。

### 協定與版本

- 新增 bridge 操作 `survey_frames`。舊版 extension 不認得這個操作，所以 `PROTOCOL_VERSION` 從 0.3.0 升到 0.4.0，版本不合時回報 `PROTOCOL_MISMATCH`，不是 `BAD_MESSAGE`。
- 新增工具屬於新功能，發 0.8.0；M1 的截圖修正一起發。

## 里程碑

每個里程碑完成後先不 commit，回報結果，等使用者同意後再 commit 並 push。

### M1：截圖不拍進協作者的游標與介面覆蓋物

- 研究 Figma 的 DOM：協作者的游標、名字標籤、選取框，檢視權限的橫幅，以及底部工具列，各自有沒有穩定的選擇器，例如 `data-testid`。
- 截圖期間以 CSS 隱藏這些元素，截完就移除，與隱藏縮放提示的做法相同。`capture`、`snapshot_layer` 與 M3 的縮圖都適用。找不到穩定選擇器的元素寫進相容性紀錄，不臆測。
- 整頁截圖依畫布背景色找出內容範圍，裁掉四周的空白。

驗證：

- 單元測試：隱藏與還原，找不到元素時照常截圖，空白裁切的邊界。
- 在私人測試檔上截整頁與單一畫面，確認橫幅與工具列不在截圖中。協作者游標要看當下是否有人在檔案中；沒遇到就寫明未驗證。
- 登入版 canary（先問使用者）。

### M2：`survey_frames`（結構）

- extension：新增 bridge 操作，逐一 frame 走訪、讀尺寸、收回、還原選取，可分次續做。
- MCP：存檔與有效期限、正規化與彙整、精簡文字輸出、工具說明。
- 重新產生 `docs/mcp-tools.md`。

驗證：

- 單元測試：分隔符號混用時的分組、元件名稱的正規化、需要人判斷的地方、自動命名比例、輸出的大小上限、存檔與權限、過期、分次續做、使用者中途介入。
- 整合測試：以圖層面板的 fixture 跑完整鏈路。
- 在私人測試檔的那個 page 實測：總時間、每個 frame 的時間、輸出大小（目標約 60 個 frame 在 40 KB 以內，約 10k tokens）、使用者的選取與圖層面板的展開狀態都還原。
- 讀尺寸的成本：每個 frame 超過 0.3 秒，或結果對判斷畫面沒有幫助，就拿掉並在紀錄中說明。

### M3：縮圖總覽

- extension：逐一截圖、縮小、拼圖、標號；MCP：存檔，回傳總覽圖。

驗證：

- 單元測試：版面計算（不同長寬比的畫面、只有一個畫面、超過一張總覽圖）。
- 在私人測試檔實測：每個 frame 的時間、總覽圖上能否認出編號與畫面標題、結束後畫面與選取還原。

### M4：skill、文件與發版

- figloo-implement 新增一節「Surveying several frames」：適用於全新 App、新功能、改版等任何涉及多個 frame 的需求，也適用於使用者只想先看全貌的時候。流程：
  1. 與使用者確定範圍，不自行切換 page。
  2. 呼叫 `survey_frames`。
  3. 向使用者簡報：流程、共用元件、同一用途的不同做法、設計師的註解，以及需要人判斷的地方。
  4. 提出快照清單與預估時間，經使用者確認後逐一快照。
  5. 每個畫面走原本的 Implementing 流程。
- skill 的 description 加上 `survey_frames`。
- 評估在 `tests/skill-eval/` 加一個案例：要求涉及多個畫面時，agent 先盤點、再問使用者，然後才快照。
- 更新 README 與繁體中文 README 的工具表、CHANGELOG、ROADMAP，以及相容性紀錄，發 0.8.0。

## 使用者的決定，2026-11-24

1. M1 不單獨發 0.7.1，和整個功能一起發 0.8.0。
2. `thumbnails` 交給 Claude 決定：工具中預設關閉，由 skill 在盤點時開啟，只要結構時的呼叫比較省。
3. 需要使用者協助時再提出，例如 M2 與 M3 的實測要在瀏覽器前景打開私人測試檔並切到那個 page。
4. 測試用的 fixture 只用通用名稱，例如「測試畫面」「資訊卡片」，不放這個檔案的名稱、連結與畫面名稱。

## 風險

| 風險 | 緩解 |
|---|---|
| 舊畫面的名稱太籠統，agent 過度相信名稱 | 盤點列出自動命名比例與需要人判斷的地方；skill 要求搭配縮圖判斷 |
| 以名稱相似歸成「同一用途」會誤判 | 標為「可能」，交給 agent 看縮圖或請使用者判斷 |
| 文字圖層改過名，註解不是文字內容 | 名稱就是 Figma 顯示的內容；必要時以 `inspect_nodes` 讀 `content` |
| 範圍大，超過一次呼叫的 3 分鐘 | 分次續做，與快照相同 |
| 截圖拍進協作者的游標與名字 | M1 修正之前，截圖只存在使用者電腦上的 `~/.figloo/`，不進 repo |
| 盤點與快照之間設計稿被修改 | 盤點與快照各有有效期限；使用者提醒時重新盤點 |
| 協定升版後，extension 與 MCP 必須一起更新 | `PROTOCOL_MISMATCH` 會說明要更新哪一邊；CHANGELOG 與發版說明註明 |
| 讀尺寸要選取 root，使用者同時操作 Figma | 沿用既有的中途介入偵測：停止並保留使用者的選取 |

## M1 結果，2026-11-24

詳見[截圖不拍進協作者的游標與介面覆蓋物](../compatibility/2026-11-24-capture-overlays.md)。

- 協作者的游標（`multiplayer-cursor-…`）、底部工具列與檢視權限橫幅（`positioned-design-toolbelt`）、留言標記的容器都在 DOM 中，截圖期間以 CSS 隱藏，截完移除。別人的選取框畫在畫布上，CSS 無法隱藏，列為已知限制。
- 整頁截圖依畫布背景色裁到內容範圍：私人測試檔的那個 page 從 982×1568（縮小到 0.84 倍）變成 1135×1079，不必縮小。
- 真實的 Figma 上，整頁、圖示與高的畫面三張截圖都沒有游標、橫幅與工具列；截完後介面恢復顯示。
- 沒有驗證：實際顯示的留言標記、登入版 canary 與訪客整合測試、深色或有圖案的畫布背景。

## M2 結果，2026-11-24

詳見[盤點多個 frame：`survey_frames`](../compatibility/2026-11-24-frame-survey.md)。

- 私人測試檔一個 160 個頂層圖層的 page：70 個 frame、7,596 個圖層，一次呼叫 31 秒，結果 27.9 KB。每次限 12 秒時分 5 次完成，概覽與一次呼叫的結果相同。
- 讀尺寸每個 frame 約 70 ms，保留。
- 依實際結果調整了「可能是 detach 的元件」與「不同名稱」的規則，並把只用在一個 frame 的元件合成一行。
- 和設計不同的地方：沒有「依相似度分群」，分群交給 agent；尺寸只讀 Frame、Auto layout、Component 與 Component set。
- 沒有驗證：有 section 的 page、以 refs 指定範圍、盤點中按 Stop、訪客與編輯權限、超過 2,000 層的 frame。

## M3 結果，2026-11-24

詳見[盤點多個 frame](../compatibility/2026-11-24-frame-survey.md)的「縮圖總覽」。

- 改為獨立的工具 `survey_thumbnails(contextId, survey, frames?)`，以 survey 的 `#n` 指定 frame；縮圖與總覽圖不存檔。理由：分次續做時不必重送概覽，agent 也能只要部分 frame。
- 每個 frame 約 1.4 秒，24 個 34 秒；每張總覽圖 12 個 frame，畫面認得出來，標題讀得到。
- 分次續做在真實的 Figma 上驗證過；截圖途中使用者介入、分頁進入背景與截不到的 frame 沒有。
