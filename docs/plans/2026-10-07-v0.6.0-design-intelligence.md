# v0.6.0：設計理解

日期：2026-10-07
狀態：M1 到 M4 完成（2026-10-07），等待發版
依據：[產品化計畫](2026-10-06-productization-and-reliability.md)第 30 到 33 節與 v0.6.0

## 目標

從「讀得到 Figma」進一步到「對得上專案」：agent 實作時，設計稿的每個顏色、文字樣式、間距與圓角都落在專案既有的 token 上，重複的圖樣用專案既有的元件，而不是把 Figma 的原始值寫死。

## 現況

- `summarize_snapshot` 已經列出每個顏色（附用途）、文字樣式、間距、padding、圓角、邊框、陰影與元件變體，各附使用次數與 ref；值是 Figma 顯示的原樣，例如 `#D5D5D5`、`PingFang TC 15px`。
- figloo-implement 的第 5 步要求 agent 自己搜尋專案、自己把摘要對到 token 與元件。真正困難的部分都落在 agent 身上：
  - 找出 token 定義在哪些檔案；
  - 跨格式比對數值：CSS 的 `#hex` 與 `rgb()`、iOS 的 `Color(red:green:blue:)` 浮點數與 asset catalog、Android 的 `0xFFRRGGBB` 與 `colors.xml`；
  - 判斷相近的值，例如設計稿 `#D5D5D5` 與專案 `#D6D6D6`。
- skill 的 eval 只檢查 skill 有沒有觸發。`claude plugin eval` 有 `tool_order`、`tool_used` grader 與 `evals/mocks/<server>/<tool>.md` 假回應，可以檢查工作流程的呼叫順序；以 `.mcpb` 網址宣告的伺服器能不能用假回應，文件沒寫，要實測。

## 里程碑（依建議的選項）

每個里程碑完成後先不 commit，回報結果，等使用者同意後再 commit 並 push。

### M1：專案 token 比對（新工具）

- 新工具 `map_tokens`：讀一份快照的摘要，掃描專案目錄中的 token 定義，回傳每個設計值對到的專案 token（檔案、行號、原始寫法），分成完全相同、相近與沒有對到三種，並列出掃到的 token 來源。
- 只讀專案目錄（`CLAUDE_PROJECT_DIR`，否則工作目錄），略過 `node_modules`、`.git`、建置輸出與大型檔案，有檔案數與時間上限。
- 顏色以 RGBA 比對，相近以色差判斷；間距與圓角以數值比對；文字樣式以字型、字重、字級比對。
- 支援的格式依「待決定」第 2 題。

驗證：每種格式各一份小型 fixture 專案，單元測試完全相同、相近與沒有對到的判斷；以本機真實快照對一個範例專案跑一次。

### M2：元件候選

- 同一個工具也依 instance 名稱，在專案原始碼中找名稱相近的元件（例如 `Button / Primary` 對到 `PrimaryButton`、`button-primary`），列出檔案與符號，交給 agent 判斷沿用、擴充或新增。

驗證：fixture 專案的單元測試。

### M3：figloo-implement 的對應步驟

- 第 5 步改為先呼叫 `map_tokens`：完全相同的直接用，相近的列出來請使用者決定沿用或新增，沒有對到的照專案的方式新增；元件候選逐一確認。
- 回報時附上對應表：設計值、專案 token、對應方式。

驗證：skill 的 trigger eval 維持通過；M4 的 workflow eval。

### M4：workflow eval

- 先實測假回應對 `.mcpb` 宣告的伺服器是否有效。有效的話，新增 eval：「實作選取的畫面」必須依序呼叫 `get_status`、`snapshot_layer`、`summarize_snapshot` 或 `map_tokens`，而且不先呼叫 `export_assets`。
- 無效的話，把結果寫進相容性紀錄，改為在本機以腳本檢查，不放進 CI。

### M5：文件與發版

- 工具文件、README 的工具表、相容性紀錄、CHANGELOG；新增工具屬於新增功能，發佈 0.6.0。

## 使用者的決定，2026-10-07

1. 新增伺服器端的 `map_tokens`。
2. 第一批支援 Web（CSS 變數、SCSS、Tailwind 設定、JSON design tokens、TS 物件）、iOS（asset catalog 的 colorset、Swift 的 `Color` 與 `UIColor`）、Android（`colors.xml`、`dimens.xml`、Compose 的 `Color`）與 Flutter，四種都要。
3. 相近的值也回報，交給 agent 與使用者決定。

## 風險

| 風險 | 緩解 |
|---|---|
| 掃描大型專案太慢或讀到不該讀的檔案 | 只讀專案目錄，略過常見的建置與套件目錄，限制檔案大小、數量與時間；不讀 `.env` 這類檔案 |
| 以正規表示式抓 token 定義會誤判 | 每種格式只抓有名稱的定義，例如 CSS 變數、`colors.xml` 的 `name`；誤判的代價是多一個候選，由 agent 決定 |
| 工具數量增加 | 這是新的操作能力（讀專案），符合「只有新能力才加工具」的原則；元件候選併在同一個工具 |

## 實作結果，2026-10-07

- M1、M2：`map_tokens` 與元件候選完成，細節與驗證見[相容性紀錄](../compatibility/2026-10-07-map-tokens.md)。實作時決定，只設定字級的 token（例如 CSS 的 font-size 變數）算相近，並註明沒有設定字重。
- M3：skill 第 5 步改用 `map_tokens`。
- M4：假回應對 bundle 宣告的伺服器無效，改用不發佈的測試外殼 `tests/skill-eval/`。案例全部通過；但換回舊版 skill 也通過，因為工具說明本身就帶出這個流程，所以這個評估守的是整體工作流程，不是 skill 的文字。
