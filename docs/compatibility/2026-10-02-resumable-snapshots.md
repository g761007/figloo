# 分段續讀的快照（snapshot_layer 最多 2,000 層）

狀態：實作完成。在使用者的 Arc 上以較短的時間上限，把 203 層的 frame 分兩次讀完，結果與一次讀完的完全相同；超過 400 層的真實圖層未驗證  
日期：2026-10-02  
範圍依據：[Roadmap 第一批](../plans/2026-10-02-roadmap-batch-1.md)的 M5

## 內容

| 項目 | 內容 |
|---|---|
| 上限 | 快照最多 2,000 層，原本是 400 層。每次呼叫仍最多 3 分鐘 |
| 續讀 | 一次讀不完時回傳 `complete: false` 與 `progress`，不附截圖與大綱；以同一個 root 再呼叫，就從停下的地方接著讀，直到 `complete: true` |
| 每次呼叫 | 都會縮放到 root、重新走一遍圖層面板、重新讀 root（用來得到這次的縮放比例），再從上次停下的圖層讀起。距離截止時間剩下 5 秒加上每個已展開列 0.1 秒時，就停在兩個圖層之間 |
| 結構改變 | 以每層的 `ref|parentRef` 比對上次的走訪；不同就代表設計稿改了，從 root 重新讀，並換用這次的截圖 |
| 定位 | 這次讀的圖層，如果位置要由屬性面板推算，而它的 frame 是前幾次讀的，就用前幾次的位置推算 |
| 檔案 | 讀到一半的快照存成 `<root>.partial.json/.jpg`，與完整的快照檔分開，期限從第一次呼叫起算。讀完才寫入完整檔並刪除 partial；`refresh: true` 會捨棄 partial |
| 讀取中 | 有 partial 時，`snapshot_layer` 一律接著讀，不回傳舊的快照；`query_snapshot`、`summarize_snapshot` 與 `export_assets` 回報 `SNAPSHOT_INCOMPLETE` |
| 背景 | 讀到一半時分頁進入背景、時間又用完，會在分頁回到畫面後才收回圖層面板 |
| 測試用的時間上限 | MCP 伺服器的環境變數 `FIGLOO_SNAPSHOT_TIME_BUDGET_MS` 可以縮短每次呼叫的時間，只供測試 |

## 做法

- 環境：Arc，已登入、檢視權限，英文 UI，使用者提供的私人測試檔；新版 MCP 伺服器以 stdio 腳本在 47130 port 啟動。
- 先以正常的時間上限讀 frame 999:61586（203 層）並保存一份，再以較短的上限分段讀同一個 frame，逐層比對兩份。

## 驗證

| 項目 | 結果 |
|---|---|
| 每次 45 秒 | 第一次讀 189 層（22.4 秒），第二次讀完其餘 14 層（8.9 秒） |
| 每次 40 秒 | 第一次讀 123 層（17.2 秒），第二次讀完其餘 80 層（13.8 秒） |
| 與一次讀完的比對 | 兩次都是 203 層、ref 順序相同，位置差 0.0 px；隱藏、匯出設定與屬性面板內容都相同，位置來源的分布也相同 |
| 已有完整快照時以 `refresh: true` 分段重讀 | 實測時發現第二次呼叫回傳了舊的完整快照，沒有接著讀；修正後有 partial 時一律接著讀，並以單元測試涵蓋 |
| 一般大小的 frame | 213 層與 90 層的 frame 各一次就讀完，分別 24 秒與 13 秒 |

## 未驗證

- 超過 400 層的真實圖層：測試檔中找不到。掃描兩個頁面的頂層 frame 後，試讀的都在 90 到 213 層之間。
- 「依前幾次已定位的 frame 推算位置」只由單元測試涵蓋：這個 frame 中以屬性面板定位的 2 個圖層都在第一次呼叫讀到，它們的 frame 是 root。
- 一個 2,000 層的快照實際要分幾次、每次走訪與收合要多久。
