# 多個工作階段的交接

狀態：已實作，以腳本啟動的伺服器、整合測試與真實的 Claude Code 工作階段驗證  
日期：2026-10-02  
規劃：[多個工作階段：自動交接與身分顯示](../plans/2026-10-02-multi-session-handover.md)

## 行為

| 情境 | 行為 |
|---|---|
| 只有一個工作階段 | 與之前相同 |
| 待命的工作階段呼叫需要 Figma 的工具，持有者閒置 | 持有者以關閉碼 4010 交出 extension，extension 200 ms 後連上新的持有者，原本的請求接著執行 |
| 持有者忙碌：有請求正在進行，或最後一次請求結束不到 10 秒 | 請求的一方回報 `BUSY`，寫出持有者的名稱 |
| 持有者結束 | 待命的伺服器每 3 秒重試，第一個成功的成為持有者 |
| 待命時呼叫 `get_status` | 列出持有者的身分與它最後收到的分頁（`tabsFresh` 為 false），不觸發交接 |
| 持有者是 Figloo 0.1.0 | 回報那個工作階段執行舊版，需要重新啟動 |
| 持有者沒有回應 | 2 秒後回報，請使用者關閉那個工作階段 |

工作階段的名稱由 MCP client 的 `title`（沒有時用 `name`）、`CLAUDE_PROJECT_DIR` 的資料夾名稱與啟動時間組成，例如 `Claude Code · shop (started 09:15)`。工具列提示、popup 與選項頁面顯示 extension 正在服務的工作階段；選項頁面另外顯示最近一次交接的時間。

## 驗證

| 項目 | 環境 | 結果 |
|---|---|---|
| 單元測試 | 同一個程序裡的兩個伺服器與假 extension | 閒置時交接、忙碌時回報 `BUSY`、10 秒緩衝、持有者結束後接手、舊版持有者、沒有回應的持有者、錯誤的 token、帶 `Origin` 的請求、待命時列出持有者的分頁，全部通過 |
| 兩個以腳本啟動的伺服器 | Arc 1.167.0，macOS 27.0，已登入、檢視權限 | 輪流交接 6 次，262 到 275 ms，中位數 269 ms。每次交接後，原持有者立刻呼叫工具都得到 `BUSY`。工具列提示、popup 與選項頁面都顯示了新持有者的名稱，選項頁面也顯示了交接時間 |
| 整合測試 | Chrome for Testing（Playwright，headless），訪客分頁 | 第二個伺服器待命時列出持有者的分頁，接手約 270 ms，選項頁面顯示新的工作階段與交接時間；第二個伺服器結束後，第一個自動接回 |
| 真實的 Claude Code 工作階段 | 桌面版工作階段與 headless 的 `claude -p` | 持有 0.1.0 伺服器的工作階段關閉後，執行新版的桌面工作階段自動接手。`claude -p` 待命時看到持有者為 `Claude Code · <專案>`，以貼上的 `tabId` 呼叫 `list_pages` 時從閒置的桌面工作階段接手；結束後桌面工作階段約 1 秒內接回 |

## 已知限制

1. Figloo 0.1.0 的伺服器不支援交接，待命時也不會重試，需要重新啟動那個工作階段。
2. 持有者結束、由待命的伺服器自動接手時，不啟動 10 秒緩衝，讓真正需要 Figma 的工作階段能立刻接手。持有者自己呼叫 `get_status` 時會向 extension 更新分頁，也算一次請求。
3. 選項頁面的「最近一次交接」只記錄因請求而交接的時間；持有者結束後的自動接手不記錄。
4. 工作階段名稱只精確到分鐘，同一個專案在同一分鐘啟動的兩個工作階段名稱相同；`get_status` 的 `holder.pid` 可以區分。
5. 真實工作階段之間的 `BUSY` 沒有另外測試，以腳本啟動的伺服器在 Arc 上驗證過。
